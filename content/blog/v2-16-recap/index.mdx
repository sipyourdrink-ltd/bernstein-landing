Grouped so the trajectory reads from one page. Three themes carry the cycle: an output-economy suite that turns token spend from a post-hoc surprise into a per-task budget with an attributed ledger; the deterministic, auditable core hardened so a run replays byte for byte and the audit chain covers the parts that used to fall outside it; and a Windows adapter path fix that stops the dominant install route from failing on a whole platform.

## the output-economy suite

The problem was never the total bill. It was that the total arrived at the end, unattributed, with no line item you could point at. A plan would spend more than expected and there was no per-task answer to where it went.

The 2.16 suite makes output spend a first-class, bounded quantity:

- **A run budget that actually stops the run.** `--max-cost-usd` is a run-level cap that stops the run once the budget is spent, so spend has a hard ceiling before anything else trips.
- **An attributed ledger, not a total.** Every token charge is written against the task, the step, the adapter, and the model that incurred it. `bernstein cost` reads back a line-item breakdown (`bernstein cost --by profile` groups it per response-style profile), so "the run cost more than I planned" becomes "this task on this model was 60 percent of it."
- **A calibrated forecast, scored.** The cost guard forecasts spend before a step runs and logs the forecast next to the actual. The forecast log is Brier-scored, so the guard's confidence is measured against outcomes rather than asserted. A guard that is systematically over- or under-confident shows up as a number, not a vibe.

Honest framing: this is an economy of *output* - the tokens the agents emit and the calls they make - not a model-pricing oracle. It reads the usage each adapter reports and holds you to a budget against it. It does not renegotiate anyone's per-token rate. What it removes is the class of surprise where the spend was real, correct, and completely un-attributed until the invoice.

## deterministic, auditable orchestration - hardened end to end

The determinism was the point from the first release. This cycle spent its correctness budget making it hold under the cases that used to slip.

The coordinator has no model in the loop: given the same seed, the same plan, and the same state, it schedules the byte-identical task graph. That property is now tested as a property, not a hope - two runs from the same inputs are compared by hash, and a divergence is a failure, not a flaky retry. The audit chain follows the same rule. Every scheduling decision, every task transition, and every artefact edit lands as an HMAC-chained entry, and the coverage gaps that used to sit *outside* the chain - a state move here, a merge there - were closed so the log reads back as one continuous record.

The compliance surface ships a verifier you do not have to trust the orchestrator to run. `bernstein compliance pack` produces a signed bundle; the standalone `bernstein-verify` wheel checks it with `cryptography` and `click` as its only dependencies, and its own test asserts that `import bernstein` raises `ModuleNotFoundError` from inside its venv - because independence from the thing it audits is the property an external reviewer actually wants.

Same caveat as the 2.x recap, restated because it still holds: this is code an evaluator can stand up and read, with tests and runbooks. It has not been through an external regulatory audit. Treat it as a verifiable artefact, not an attestation.

## the Windows adapter path fix

This is the unglamorous one, and it is the most important line in the release for anyone on Windows.

The standard install path - `pipx install bernstein`, point it at a wrapped agent, run a plan - broke on Windows whenever the agent CLI was installed as a `.cmd` or `.bat` shim, which is how npm-installed CLIs (Codex via nvm-windows, for example) land on that platform. The worker spawned the bare binary name, and Windows does not apply `PATHEXT` extension resolution to a bare `argv[0]`, so a binary that was genuinely present and on `PATH` could not be started.

The fix, shipped in 2.16.1, does two things:

- **Absolute-path resolution.** The worker resolves the adapter binary to its absolute path before spawning, so a Windows agent binary on `PATH` resolves the same way its POSIX sibling does. Real executables and all POSIX spawns are unchanged.
- **Shims through the command interpreter.** Resolved `.cmd` / `.bat` shims are routed through the command interpreter on Windows, and `PATHEXT` is passed through the worker environment.

Why this matters more than a normal bug: the platform install path most people follow is the one that has to work without a support thread, and on Windows it did not. A regression that only surfaces through user reports is exactly the class that costs the most to run down, because by the time it reaches you it has already cost someone else an afternoon. This closes it.

## upgrading

```bash
pipx install --upgrade bernstein     # or: pip install --upgrade bernstein
```

That is the whole upgrade. 2.x configs and plans run unchanged - `bernstein run`, `bernstein conduct`, `bernstein live`, `bernstein gui serve` all behave as before. The new cost surfaces are opt-in through `--max-cost-usd` and the existing `bernstein cost` view; nothing you already have needs to move.
