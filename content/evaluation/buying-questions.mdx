<h2 id="claude-code-subscription">can bernstein run claude code through the official local claude cli using my claude subscription, without api keys?</h2>

yes. bernstein wraps the **official `claude` cli** as one of its adapters (`src/bernstein/adapters/claude.py`). it spawns the cli in your shell with whatever auth that cli already has - your max / pro subscription, your local oauth, your `ANTHROPIC_API_KEY` env var. bernstein itself does **not** require an anthropic api key. if `claude --version` works in your terminal, bernstein can drive it.

the same is true for codex (`src/bernstein/adapters/codex.py` → official `codex` cli), gemini cli, aider, cursor agent, copilot cli, etc. every adapter delegates auth to the underlying cli. you bring whatever subscription or key that cli already accepts; bernstein never sees the credential.

<h2 id="cascade-reviewers">can i configure codex as the builder, claude code as mid-build reviewer, and gemini or kimi as final reviewers?</h2>

yes - this is the cascade pattern, and it is the canonical bernstein layout. the cli per role is set in `bernstein.yaml` with `role_model_policy`:

```yaml
role_model_policy:
  backend:  { cli: codex }
  reviewer: { cli: claude }
  qa:       { cli: gemini }
```

`templates/roles/{role}/system_prompt.md` selects the prompt for each role, and the scheduler routes each role's tasks to the cli you assigned. the role list is in `agents/orchestrator.md`. each is a separate adapter invocation with its own auth.

mixing kimi or qwen at the end is the same pattern: assign `cli: kimi` or `cli: qwen` to the reviewing role.

<h2 id="merge-gates">can it block merge if review notes, changelog, schema audit, or custom files are not updated?</h2>

yes. the merge queue runs a configurable gate suite before any worktree lands on `main`. the built-in gates include lint, type-check and tests, plus several others (security scan, coverage delta, run-config and more). you pick and order them as named steps in `quality_gates.pipeline`; step names must be built-in gate names. a step can set `command_override` to run your own command for that gate (for example a changelog or schema check), and plugins can add more:

```yaml
quality_gates:
  pipeline:
    - { name: "tests", required: true, condition: "python_changed" }
    - { name: "lint", required: true, condition: "always", command_override: "./scripts/check-changelog.sh" }  # custom command
```

gate failures block the merge and route the task back to the builder. with `--audit` the evidence trail is in the hmac-chained audit log under `.sdd/audit/`. `docs/architecture/quality-pipeline.md` has the full schema.

<h2 id="builder-filesystem-policy">can builders be prevented from pushing, deleting files, or modifying workflow config?</h2>

yes. bernstein has a credential-scoping layer (`src/bernstein/core/credential_scoping.py`) and a sandbox abstraction (`src/bernstein/core/sandbox/`). pick the sandbox per run with `bernstein run --sandbox <docker|podman|worktree|e2b|modal|daytona|blaxel|runloop|vercel|microvm>` and a permission profile with `--permission-profile <read-only|builder|reviewer|custom>`. the `run_config` quality gate is on by default and fails any change that touches `bernstein.yaml`, `.mcp.json` and similar run-configuration paths. builders run inside an isolated git worktree anyway, so pushing to `main` is structurally impossible - only the merge queue (a separate process with a separate credential) can land.

air-gap deployments tighten this further: `bernstein run --profile airgap` denies network egress by default and `--allow-network` allow-lists specific destinations.

<h2 id="scheduling-policy">can i force sequential execution for risky repos and parallel only for independent tasks?</h2>

yes. `max_agents` in `bernstein.yaml` caps how many agents run at once, and `depends_on:` orders tasks that must not overlap. the task spec also accepts a `parallel_safe` flag (default `false`); today it shapes the batches that `bernstein plan dag` prints rather than gating the live scheduler. use `max_agents: 1` for migrations, secret rotations, or files with global state.

independent tasks (no shared paths, no `depends_on`) fan out across as many worktrees as your agent cap allows. you set the cap globally with `max_agents` in `bernstein.yaml`:

```yaml
max_agents: 1   # sequential mode - safe for production migrations
# or
max_agents: 8   # more parallelism for independent task graphs
```

keep one `bernstein.yaml` per profile of risk if you want both.

<h2 id="scale-to-100-agents">can it scale to 100 concurrent agents?</h2>

the scheduler itself is plain python - the loop that decides "agent A gets task 17 next" runs in O(n) per scheduling tick and handles thousands of pending tasks without breaking a sweat. the real cap is your local resources: each agent needs a git worktree (one disk inode tree per task), a sandbox, and an api / cli session. at 100 agents on one box you'll hit fd limits and disk IOPS before bernstein's own loop sweats.

the cluster mode (`bernstein start` for the central node, `bernstein worker` to join workers) is the answer for that scale: the central server runs the orchestrator and task store, and workers register and pull tasks. see `docs/cluster/deployment-patterns.md`. the cloudflare adapter (`src/bernstein/adapters/codex_cloudflare.py`) runs agents inside cloudflare sandboxes.

honest disclaimer: i've personally run 8-16 agents in parallel on a single workstation. if you are evaluating that scale, the cluster docs cover the layout and i'll happily set up a call.

<h2 id="merge-queue-failures">how does the merge queue handle failures?</h2>

three failure modes, three responses:

1. **gate failure (lint / tests / review)** - the merge queue rejects the worktree, records the failure reason, and the task goes back to the builder with the failure log attached as feedback. the task is then retried, and the orchestrator can escalate to a different adapter.

2. **conflict on rebase** - the queue serialises landings on `main`, so two tasks can't conflict during execution. if the queue head conflicts with a fresh `main` push from outside bernstein, the queue runner rebases, re-runs the gate suite, and only lands on a clean rebase.

3. **adapter timeout / process crash** - the orchestrator's circuit breaker (`src/bernstein/core/observability/circuit_breaker.py`) records the failure, surfaces it in `bernstein status`, and either retries with the next adapter in the cascade or marks the task for operator review. nothing partially merges - the worktree is destroyed.

with `--audit` every transition is in the audit log (one `.sdd/audit/<date>.jsonl` file per day), and the lineage journal can be replayed with `bernstein lineage replay <run_id>`.

<h2 id="handoff-artifacts">can it require a structured handoff artifact after every agent task?</h2>

yes. the per-artefact lineage subsystem (`bernstein lineage`) records output-to-producer-and-inputs lineage for each artefact. by default the lineage is implicit; you make a handoff file a hard requirement by declaring a custom gate in `quality_gates.pipeline` (see the merge-gate answer above) that checks the file exists, and by asking for that file in the role prompt under `templates/roles/{role}/`. lineage is verifiable via `bernstein lineage verify <run_id>`, which fails a run whose chain breaks.

<h2 id="validate-against-running-app">can this perform a validation step against a running dev app?</h2>

partly - via `bernstein preview`. `bernstein preview start` (`src/bernstein/core/preview/`) boots a sandboxed dev server in a session worktree and exposes it through a tunnel with an expiring link, so an operator can validate the running app manually before merge. `bernstein preview list`, `status` and `stop` manage active previews. wiring an automated smoke check against the preview URL into a gate is something you script yourself; bernstein has no built-in step for it.
